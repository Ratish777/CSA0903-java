# CO1 – Campus Smart-Parking System (written answers)

## Task 1 – Problem analysis
Inputs: registration number, vehicle category, user category/pass ID, entry/exit time, requested charging, floor/slot configuration. Outputs: allocated floor and slot, unique ticket, occupancy, parking duration, fee/waiver, error if full or invalid. Candidate classes: `Vehicle` (identity and fee behaviour); `TwoWheeler`, `Car`, `ElectricCar` (specialised rates/capabilities); `ParkingSlot` (one vehicle and occupied state); `ParkingFloor` (slots and search); `ParkingFacility` (allocation/release and capacity); `ParkingTicket` (ticket ID and entry time); `ParkingUser`/`MonthlyPass` (eligibility and validity); `FeeCalculator` (pricing policy). Nouns become model classes; verbs such as allocate, release, issue, validate and calculate become methods. Rules: one vehicle per slot; allocate only compatible vacant slot; ticket IDs unique and never reused; entry time recorded once; exit requires active ticket; release only after successful checkout; valid student/staff pass means zero parking fee; visitors pay; EV charging is separate. Assumptions: registration is unique while parked; times use local date-time; rates are configurable; slot numbering is unique within a floor; pass validity is checked at entry and exit.

Alternative arrays: parallel arrays `regNo[]`, `type[]`, `entryTime[]` require matching indexes and O(n) search; adding an attribute requires another synchronized array. Objects also require O(n) search without an index and O(n) storage, but encapsulate fields and behaviour and make adding an attribute safer. A `HashMap<String,Vehicle>` would make average lookup O(1) at extra index memory.

## Task 2 – Data representation
`int` for floor/slot/route; `String` for registration and ticket IDs (leading zeros/letters matter); `LocalDateTime` for entry/exit; `long` for elapsed minutes; `double` or preferably `BigDecimal` for currency. Use a jagged `String[][]`/`ParkingSlot[][]` because each floor may have a different slot count. Read interactive input with `Scanner`, validate before conversion. Avoid `minutes / 60` integer truncation: 61/60 is 1, but every started hour bills 2. Use `(minutes + 59) / 60`; use `long` for large durations. A flat array index formula only works cleanly for equal slots per floor; jagged arrays support different sizes directly. Search time O(total slots), storage O(total slots); flat array also O(total slots), with constant-time index calculation.

## Task 3 – Control logic
Allocation pseudocode: FOR each floor; FOR each slot; IF slot is empty AND compatible THEN assign vehicle and RETURN floor,slot; END IF; END FOR; END FOR; RETURN NO_SLOT. Fee pseudocode: validate minutes >= 0; billableHours = (minutes+59)/60; fee = first-hour rate plus additional-hour rate for remaining hours; fee = MIN(fee,dailyMaximum); IF valid monthly pass THEN fee=0; return fee. `break` exits an inner search when a match is found; `continue` skips occupied/incompatible slots; `return` ends allocation immediately. No free slot returns null or a domain-specific failure. `ParkingFacility.java` implements the supplied TODOs; expected output is reproduced by running it.

## Task 4 – Classes and constructors
Use parameterised constructors to establish required state; overload only where meaningful. `this(...)` chains constructors to one validation path. A copy constructor is useful for a defensive ticket snapshot, but ticket IDs should not be duplicated. Local reference variables are on stack frames; objects are allocated on heap; references point to objects. Factory methods can validate and return configured instances; setters allow temporarily invalid objects unless validation is repeated.

## Task 5 – Static and lifecycle
A static ticket sequence is shared by all tickets; static occupancy can represent facility-wide totals only if the design truly has one shared facility. For separate north/south facilities, keep occupancy per facility and use a shared `AtomicLong` ticket generator if IDs must be globally unique. Static data uses one class-level field; an instance counter uses one field per facility object. After checkout, when no references remain to a ticket/vehicle, it becomes eligible for garbage collection; collection timing is JVM-controlled.

## Task 6 – Inheritance
`Vehicle` is the superclass; `TwoWheeler` and `Car` are subclasses (hierarchical inheritance); `ElectricCar extends Car` (multilevel). `ElectricCar` adds charging capability. `super(regNo)` invokes the parent constructor before subclass initialisation. Trace: Vehicle constructor → Car constructor → ElectricCar constructor. Composition alternative: `Vehicle` has a `VehicleType` rate strategy; adding a type means adding a strategy rather than subclassing. Fee lookup remains O(1); object composition adds one referenced strategy object or shared strategy reference.

## Task 7 – Overriding
Subclasses override `ratePerHour()`/`calculateFee()` with `@Override`. The signature must match; return type must be same or covariant; visibility cannot be reduced. Use `final` for immutable registration fields and stable invariants, not for extension points. `equals` and `hashCode` must use the same identity field (registration number); otherwise HashSet/HashMap behaviour is incorrect. `toString` should show readable vehicle details. A switch-based method is initially O(1) per fee but requires modifying central code for every new type; polymorphism isolates the change.

## Task 8 – Polymorphism
Overload `calculateFee(int minutes)` and `calculateFee(LocalDateTime in, LocalDateTime out)` for compile-time selection. A `Vehicle[]` can hold subclass objects (upcasting); at runtime `v.calculateFee(...)` invokes the actual object's override. `FeeDemo.java` demonstrates dynamic dispatch and `Chargeable`. Expected output: TwoWheeler Rs 30.0; Car Rs 90.0; ElectricCar Rs 210.0; equality true. Equality is true because the design defines identity solely by registration number; this is appropriate only if registration is globally unique across vehicle types.

## Task 9 – Abstraction
`Vehicle` should be abstract because a generic vehicle has no universal rate; `ratePerHour()` is abstract. `Chargeable` is an interface because charging is a capability only some vehicles possess and Java permits multiple interfaces. An interface can provide default behaviour or static utility methods. If Vehicle were an interface, shared instance state and constructors would be unavailable; each implementation would duplicate or delegate state. Interfaces support multiple implementation inheritance.

## Task 10 – Encapsulation and packages
Suggested packages: `parking.model` (Vehicle, Slot, Ticket), `parking.service` (allocation, fee policies), `parking.app` (main/UI), `parking.persistence` (repository). Fields private; constructors/methods public only where needed; protected for subclass extension points. Setters validate ranges and reject null/blank identifiers. Wrapper equality must use `.equals`, not `Integer ==`, because object identity is not numeric equality. Autoboxing can create null-unboxing `NullPointerException`.

## Task 11 – Implementation and validation
Test: first allocation, next slot, full facility, invalid floor/slot release, repeated release, reallocation after release, negative duration, zero duration, 61-minute billing, valid pass waiver, visitor fee, EV charging. Record expected and actual results and attach IntelliJ screenshots after running. Core scans are O(F×S); fee calculation O(1); memory O(F×S + V) for slots and active vehicle/ticket records.

## Task 12 – Re-evaluation
Retain the object-oriented model but modify pricing to Strategy (`PricingPolicy`) and vehicle capabilities to interfaces. Add a new vehicle category by supplying a new subtype/type strategy; add a new pricing rule by implementing another policy. Avoid changing existing allocation/ticket classes (Open/Closed Principle). Add automated regression tests for allocation, checkout, passes, EV charging and new pricing. The fee policy is selected/configured, not embedded in a long switch.
